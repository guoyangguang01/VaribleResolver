# 工程执行工具重构方案

## 1. 文档目的

本文档定义工程执行能力的重构方案，目标是：

- 将工程执行逻辑收敛到独立的执行工具。
- 将文件复制、路径归一化、工程可移植性交给工程生成阶段。
- CLI、UI 和测试只调用执行工具，不重复实现执行能力。
- 执行工具每次只执行一个场景。
- 移除基线运行和覆盖结果比较功能。
- 仅校验本次覆盖涉及的输入参数及其定位规则。
- 执行结束后返回实际输入值和输出参数值。

本文档只描述方案，不包含代码实现。

## 2. 当前问题

当前工程执行相关能力存在以下问题：

1. CLI 封装层包含文件读写、进程启动和程序运行实现。
2. CLI 曾提供 `--compare-baseline`，导致一次请求可能执行两次程序。
3. UI、CLI 和测试可能维护不同的执行路径。
4. 输入参数校验和文件写入没有形成清晰的统一边界。
5. 生成后的工程仍可能引用原始绝对路径，执行阶段不得不承担复制和恢复责任。
6. 文件恢复、进程启动和输出提取与具体运行环境耦合，复用和测试成本较高。

## 3. 目标与非目标

### 3.1 目标

- 建立唯一的工程执行工具。
- 使用适配器隔离文件系统和进程操作。
- 保持 CLI 封装层足够薄。
- 让测试直接调用执行工具。
- 使用标准请求结构，按 `文件名 + 参数名` 复合主键覆盖输入值。
- 未覆盖的输入参数不扫描、不校验、不写回。
- 工程生成时复制绑定文件，并将运行路径全部归一化到生成工程内部。
- 执行工具直接使用生成工程中的绑定文件，不处理原始文件副本或恢复。
- 返回运行时状态、实际输入值和输出参数值。

### 3.2 非目标

- 不比较基线和覆盖运行结果。
- 不自动执行两次程序。
- 不计算输出数值差、相对差或等价状态。
- 不保存执行历史。
- 不提供参数扫描或批量实验。
- 不在封装层中实现文件操作或进程启动。
- 不在执行工具中复制原始工程文件。
- 不在执行工具中改写程序路径或原始绝对路径。
- 不在执行工具中恢复输入、输出绑定文件。

## 4. 总体架构

```text
原始文件
   |
   v
ProjectGenerator
  - 复制绑定文件到生成工程
  - 改写为工程内相对路径
  - 校验工程自包含性
   |
   v
生成后的自包含工程
   |
   v
CLI / UI / 测试
      |
      v
使用入口：参数解析、工程加载、结果格式化
      |
      v
ProjectExecutionTool
  - 标准覆盖请求解析
  - 覆盖目标定位校验
  - 覆盖参考工程中的输入副本
  - 程序启动
  - 输出提取
      |
      v
ProjectExecutionPorts
  - 文件系统适配器
  - 进程运行适配器
```

执行工具是唯一的执行入口。使用入口只负责准备请求和展示结果。

## 5. 执行工具接口

### 5.1 请求

```ts
interface ProjectExecutionRequest {
  snapshot: ProjectExecutionSnapshot;
  overrides: ProjectInputOverride[];
}
```

标准覆盖结构：

```ts
interface ProjectInputOverride {
  fileName: string;
  parameterName: string;
  value: string;
}
```

文件名和参数名组合必须唯一；不同文件允许使用相同参数名。同一次请求中不允许重复覆盖同一个主参数。

### 5.2 结果

```ts
interface ProjectExecutionResult {
  runtime: ProjectProgramResult;
  inputs: EffectiveInputValue[];
  outputs: OutputExtraction[];
}
```

结果中不再包含：

- `baseline`
- `comparisons`
- `numericDelta`
- `relativeDelta`
- `equivalent`
- 两次运行结果

### 5.3 执行方法

```ts
interface ProjectExecutionTool {
  execute(
    request: ProjectExecutionRequest,
  ): Promise<ProjectExecutionResult>;
}
```

## 6. 执行依赖接口

执行工具不直接依赖 Electron、Node.js 文件系统或子进程 API。

```ts
interface ProjectExecutionAdapter {
  readFile(
    filePath: string,
  ): Promise<ProjectExecutionReadFile | null>;
  writeFiles(
    files: WrittenFile[],
  ): Promise<unknown>;
  runProgram(
    request: ProjectProgramRequest,
  ): Promise<ProjectProgramResult>;
}
```

执行端口只处理生成工程中的路径。执行工具不得通过端口访问工程生成前的原始绑定路径。

建议提供两类适配器：

| 适配器 | 用途 |
|---|---|
| `LocalExecutionAdapter` | CLI 使用本地文件和子进程 |
| `DesktopExecutionAdapter` | UI 通过 Electron 桥接文件和进程 |
| `MemoryExecutionAdapter` | 单元测试使用可控内存文件和进程结果 |

## 7. 职责划分

### 7.1 工程生成

工程生成阶段负责：

1. 将输入、输出绑定文件复制到生成工程内部。
2. 将绑定和启动配置中的运行路径改为工程内相对路径。
3. 将原始绝对路径仅作为来源元数据保存，不参与执行。
4. 校验所有绑定文件均存在于生成工程内部。
5. 校验程序工作目录位于生成工程内，或明确声明为只读外部依赖。
6. 对无法自包含的工程拒绝生成或给出明确警告。

生成工程是执行工具的唯一输入。执行工具不得重新解析原始文件路径，也不得决定何时复制或恢复原始文件。

工程生成完成后应满足：

- `bindings[].filePath` 指向生成工程内部文件。
- `files[].path` 指向生成工程内部文件。
- 原始路径只出现在来源信息中。
- 启动参数和工作目录不依赖原始文件副本。

### 7.2 执行工具

执行工具负责：

1. 接收生成工程快照和标准覆盖请求。
2. 校验未知参数、重复参数、输出参数误覆盖和参数值类型。
3. 定位本次覆盖涉及的输入参数。
4. 生成写回内容，并确保所有覆盖目标都能成功定位。
5. 将覆盖后的输入参数写入生成工程中的文件。
6. 生成程序参数并启动程序。
7. 读取生成工程中的输出绑定文件并提取输出参数。
8. 返回本次执行结果。

执行工具不执行全量预检。只解析本次覆盖涉及的输入绑定及其定位规则；未覆盖的输入参数不额外扫描或校验。任意覆盖目标定位失败时停止本次执行，不启动程序。由于生成工程或运行工程副本可丢弃，已经发生的副本修改不需要恢复。

各定位模式的具体规则以[现有定位规则文档](./variable-localization-rules.md)为准。

执行工具不负责原始文件保护、复制、路径改写或恢复。只要输入工程满足生成契约，执行工具就不会接触工程生成前的原始文件。

### 7.3 CLI 封装

CLI 只负责：

1. 解析 `--project`、`--set` 和 `--request`。
2. 加载目录式工程。
3. 创建 `DesktopExecutionPorts`。
4. 调用 `ProjectExecutionTool.execute`。
5. 输出 JSON 结果。
6. 将异常映射为进程退出码。

CLI 中不得保留：

- `spawn` 或 `exec` 调用。
- 文件读取、写入和删除实现。
- 程序运行适配器。
- 输出提取和比较实现。
- `--compare-baseline` 参数。
- 原值运行和覆盖运行的双执行流程。
- 原始文件复制、路径改写和恢复流程。

### 7.4 UI

UI 负责：

- 收集参数及覆盖值。
- 调用执行工具。
- 展示执行状态。
- 展示实际输入值和输出参数值。
- 展示错误信息。

UI 不得自行写文件、启动程序、提取输出或执行比较。

### 7.5 测试

测试直接调用执行工具，不实现另一套执行流程。

单元测试使用 `MemoryExecutionPorts`：

- 合法覆盖参数。
- 按完整文件名和参数名覆盖。
- 按省略扩展名的文件名和参数名覆盖。
- 文件名和参数名组合不唯一时拒绝覆盖。
- 同一绑定被重复覆盖时拒绝请求。
- 未知参数。
- 输出参数被误覆盖。
- 参数类型无效。
- 输入定位规则无效。
- 程序失败时仍尝试提取输出。
- 执行器不会访问生成工程之外的绑定路径。

集成测试使用临时目录和 `DesktopExecutionPorts`，调用同一个执行工具。

## 8. 单次执行流程

```text
1. 解析覆盖参数
2. 校验覆盖选择器和值
3. 生成覆盖目标对应的待写文件
4. 将覆盖值写入生成工程中的输入文件
5. 启动且仅启动一次程序
6. 提取输出参数
7. 返回执行结果
```

覆盖目标定位失败时终止执行且不启动程序。已经写入的文件只存在于可丢弃的运行工程副本中，执行阶段不包含保存快照或恢复文件的步骤。

## 10. 测试方案

| 层级 | 调用对象 | 验证内容 |
|---|---|---|
| 工程生成单元测试 | `serializeProjectFolder` / `parseProjectFolder` | 文件复制、相对路径和自包含性 |
| 执行工具单元测试 | `ProjectExecutionTool` + 内存端口 | 标准覆盖、定位校验、输出提取 |
| 适配器集成测试 | `ProjectExecutionTool` + 临时生成工程 | 生成工程文件读写和进程生命周期 |
| CLI 测试 | CLI 参数解析 + spy 执行工具 | 参数映射、单次调用、输出和退出码 |
| UI 测试 | UI + spy 执行工具 | 参数传递和结果展示 |

CLI 测试不得启动真实工程程序。真实进程仅在明确标记的适配器集成测试中运行。

重点测试用例：

1. 本次覆盖目标的定位规则合法时只调用一次 `process.run`。
2. 任一覆盖目标定位失败时不调用 `process.run`。
3. 完整文件名和省略扩展名的文件名都能解析到同一个输入绑定。
4. 同名参数和不存在的选择器在写盘前失败。
5. 程序返回非零退出码时，仍读取已有输出。
6. 程序超时或抛错时，执行器不访问生成工程之外的绑定路径。
7. `--compare-baseline` 不再被接受。
8. 执行结果不包含基线、输出比较或文件恢复字段。
9. 重新生成工程后，所有绑定路径仍指向新生成工程内部。

## 11. 验收标准

- 系统中只有一个工程执行工具。
- CLI 和 UI 不含程序启动及文件写回实现。
- 测试直接调用执行工具。
- 工程生成阶段完成文件复制和相对路径归一化。
- 执行工具不接触生成工程之前的原始文件。
- 基线比较功能及其数据结构已删除。
- 每次请求最多启动一次程序。
- 只校验本次覆盖涉及的输入参数，不扫描未覆盖输入。
- 执行结果包含实际输入值、输出值和运行时信息。
- 执行结果不包含文件恢复状态。
- `npm test` 与 `npm run build` 通过。

## 12. 实施阶段

### 阶段一：明确生成工程契约

- 增加生成工程内部的相对路径模型。
- 复制绑定文件并校验自包含性。
- 加载工程时只解析生成工程内部路径。

### 阶段二：收敛执行入口

- 移除基线比较及双执行流程。
- 引入标准覆盖请求。
- 删除恢复和 `keepChanges`。
- 精简执行结果。
- 将 CLI 改为调用执行工具。

### 阶段三：隔离适配器

- 提取文件和进程端口。
- 创建桌面及内存适配器。
- 将 CLI 中的执行实现迁出。

### 阶段四：统一调用方

- UI 接入执行工具。
- 测试改为调用执行工具。
- 删除重复执行代码。

### 阶段五：验证与文档

- 补齐单元、集成和 CLI 测试。
- 更新 README 和功能文档。
- 执行静态检查、构建和测试。

## 13. 风险控制

- 重构期间保持执行工具接口稳定。
- 先迁移 CLI，再迁移 UI，避免同时改动所有调用方。
- 工程生成契约必须先于执行工具改造完成，否则执行器仍可能间接访问原始路径。
- 生成工程必须通过自包含性检查，禁止把绝对运行路径重新引入执行阶段。
- 适配器迁移不得改变现有程序参数和输出提取语义。
- 不执行实际工程程序即可完成大多数自动测试。

## 14. 当前实现状态

已完成：

- 标准 `fileName + parameterName` 覆盖请求。
- `--set` 和 `--request` CLI 入口。
- 执行工具与桌面、本地、内存适配器分离。
- 删除基线比较、原文件恢复和 `keepChanges`。
- 只处理覆盖目标，不扫描未覆盖输入。
- 工程 schema v4、文件角色、输出契约和运行路径归一化。
- UI 保存生成工程后调用统一执行工具。
- UI 和 CLI 每次执行创建独立 `runs/<runId>` 工作区。
- 参考输出默认不进入运行工作区，输出参数映射到运行空间中的实际文件路径。
- 启动配置支持 direct 和 shell 模式。
- 兼容读取 schema v2/v3 工程。

尚未确定：

- 当前输出发现先支持固定路径；Glob、Manifest 和目录扫描仍待扩展。
- 程序需要的未绑定支持文件如何纳入生成工程尚未定义。
